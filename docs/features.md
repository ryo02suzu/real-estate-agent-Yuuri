# 機能要件（UI実装向け）

ロジックは `lib/roadmap` の `lookup(address)` を呼ぶだけで揃う。

## Must（これが無いと意味がない）

1. **住所入力 → 検索**
   - 1行の入力欄。コピペ前提（レインズや社内資料から貼る）。
   - `lookup()` の結果 `status` で3分岐: `ok` / `not_found` / `unsupported`。
2. **「どこを見たか」の確認表示**
   - `matchedAddress`（国土地理院が解釈した住所）と `town` を必ず出す。入力と違えば気づけるように。
   - 番地まで一致しないことがある（街区レベル）ので「〇〇付近」と表示。
3. **この市のネット公開レベル**（`municipality.coverage`）
   - `full`: 「この地図で全種別が分かります」
   - `partial`: 「位置指定道路など一部だけ。無ければ窓口へ」
   - `none`: 「ネットでは分かりません。問い合わせへ」
4. **地図を開くボタン**（`links[]`）
   - `road_type` / `designated_only` を一番上・一番大きく。`public_road` は補助。
   - `pinpoint: false` のものは「入口が開くだけ（地図内で住所検索が必要）」と明記。
   - 新しいタブで開く。利用規約の同意画面が出ることがあるが、同意後に該当地点が中心で開く、と一言添える。
5. **問い合わせ先**（`municipality.contact`）
   - 電話番号はタップで発信（`tel:`）。メールは `mailto:`。
   - `note`（「電話不可・窓口のみ」等）は目立たせる。無駄電話を防ぐため。
6. **未対応の市**（`unsupported`）
   - 「この市は未対応」＋ Googleで「〇〇市 指定道路図」を検索するリンク。

## Should（あると体験が良くなる）

7. **地図プレビュー**: 座標にピンを立てた小さい地図（国土地理院タイルなら無料）。「この場所で合ってるか」の確認用。
8. **直近の検索5件**: 端末の localStorage のみ。**サーバーに保存しない**（顧客物件の住所なので）。
9. **凡例の一言メモ**: 市ごとに「この地図の○色＝2項道路」などを1〜2行。`Municipality.note` に追記していく。
10. **住所コピー**: 国土地理院が解釈した住所をワンタップでコピー（地図側の住所検索に貼る用）。
11. **結果の共有・コピー**: 住所・公開レベル・地図のURL・問い合わせ先・「最終確認は窓口で」をまとめた文面を、スマホは共有シート、PCはクリップボードへ（`lib/summary.ts`）。上司への報告やメモ用。
12. **候補の選択**: 都道府県なしで「本町1-1」のように入れて全国に同名の場所があるときは、候補（関東を先に）から選ぶ。
13. **番地が見つからないときの注意**: 国土地理院が町・大字までしか一致しなかったら「町の中心を表示」と警告する。
14. **窓口で聞くこと**: 持ち物・聞くこと・FAX／メール用の依頼文（`lib/inquiry.ts`）。問い合わせ先から開く。
15. **地図ごとの操作メモ**: レイヤ切替や同意画面の押し方など、開いたあとに要る操作をボタンの下に出す（`MapLink.tip`）。
16. **PDF の図を選んで開く**: 図を PDF で公開している市は、物件が載っている図を座標から選んで直接開き、「物件は図の右下あたり」と図と同じ範囲の地図を出す（`MapLink.sheets`、求め方は docs/pdf-sheets.md）。
    - 市全体で1枚の図は「市全体の図」と呼び、図のどのあたりかだけを出す。
    - 地区ごとの図（範囲が重なる）は、逆ジオコーダの町名（`town`）でその地区の図を選ぶ（`SheetIndex.towns`）。
17. **地図で場所を選ぶ・直す**: 住所が分からない土地や、番地まで一致せず場所がずれたときは、地図で場所を選んで調べる（`lookupPoint(lat, lng)`）。
    - 住所の代わりに逆ジオコーダの市区町村・町名を使い、「地図で選んだ地点」「埼玉県熊谷市宮町二丁目 付近」と出す。共有の文面には、その地点を地理院地図で開く URL を添える。
    - URL は `?ll=緯度,経度`。検索履歴にも座標で残し、同じ町の別の地点は別の履歴にする。
    - スマホ：ホームの右上のメニュー（≡）の「地図で場所を選ぶ」と、結果の地図プレビューの「場所を直す」で全画面の地図を開き、中央の印を物件に合わせて「この場所で調べる」。「現在地」で現地からも選べる。
18. **PC は地図が中心**（横幅 1024px 以上）: 全面に動く地図（MapLibre GL ＋ 地理院タイル、淡色・標準・写真）を敷き、左に検索と結果のパネル、右上にメニューを重ねる（`components/desktop-shell.tsx`）。
    - 物件のピンをドラッグするか、地図をクリックして「ここで調べる」で場所を選び直せる。
    - PDF の図の市は、物件が載っている図の範囲（枠と 3×3 の目安線）を地図に重ね、「図の範囲」で図と同じ範囲を表示する。
    - MapLibre は動く地図を出すときだけ読み込む。描画のワーカーは `npm run dev` / `build` の前に `public/maplibre/<版>/` に置く（`scripts/copy-maplibre-worker.mjs`）。WebGL が使えない端末では静的なプレビューに切り替える。
    - 市名の下に、スマホと同じ「都市計画（用途地域・建ぺい率・容積率など）」と「地番」の1行を出す。押すとパネルの中の詳しいカードまで動く（ノート PC の低い画面でも、最初の画面で要点が分かる）。
    - 地図を動かしていても、住所で調べ直すと（同じ住所でも、検索ボタン・Enter とも）物件のピンの場所へ戻る。
    - 「/」キーで住所の入力欄へ（入っている住所を選んだ状態になり、そのまま次の住所を打てる）。「結果をコピー」は共有の画面を出さず、メールやチャットに貼れるようコピーする。
19. **地番で探す・筆を表示する**（`lib/roadmap/parcel.ts`）: 法務省の登記所備付地図データ（筆のベクトルタイル、PMTiles・レイヤ fude・z16 に全件）をブラウザから範囲指定で読み、地番から筆の場所と形を出す。
    - 「地番 熊谷市下奈良391-3」と書くか、番地まで見つからない住所（「熊谷市下奈良391番地3」）、国土地理院が「354番地」までしか持たない住所で、町・大字の代表点のまわりのタイルを近い順に読み、地番区域（市区町村_大字_丁目_小字）と地番が一致する筆を探す。地番の数字が近い筆の方へ広げ、3タイル（約1.5km）以内に町の筆が無ければ地図データの無い地域とする。住居表示（○番○号）まで一致した住所は探さない。
    - 見つかれば「地番で探した筆」として筆の中の点を物件の場所にし、筆の形を地図に重ねる。見つからなければ町の代表点のまま、理由（地番が無い／地図データが無い）と枝番違いの近い地番を出す。ついでに探しただけ（番地まで一致した住所）のときは、見つからなくても何も言わない。
    - 地図で選んだ地点も、その地点の筆の地番を出す（`parcelAt`）。PC の地図とスマホの「地図で選ぶ」は「筆・地番」で筆界を表示でき、クリックした筆・中央の筆の地番が出る。
    - 筆の地図データは公共座標の図面だけで、公図（任意座標）しか無い所は抜けている（同じ町の中でもまだら。公図の筆を推定の位置に置いたものは 30.）。「筆・地番」「用途地域」「道路種別」を表示しても見ている範囲に何も描かれないときは、地図の上に理由を出す（データが無い・地図を拡大すると表示される・読み込めなかった）。関東全体のように引いた地図では、押しても寄らない（寄った先が物件の辺りとは限らないため）。
    - 出典は利用規約どおり「「登記所備付地図データ」（法務省）を加工して作成」と版を、地図・結果・共有の文面に出す。法務局の証明ではない旨も添える。
    - データの置き場所は `lib/roadmap/data/parcel-source.json`。最初は AMX プロジェクトの全国版（2024年4月公開版）。最新版は `.github/workflows/parcel-tiles.yml` が作って Cloudflare R2 に置き、このファイルを書き換える。
20. **都市計画（用途地域・建ぺい率・容積率・防火地域など）を出す**（`lib/roadmap/zoning.ts`）: 国土交通省「都市計画決定GISデータ」（全国都市計画決定情報GIS、商用利用可）の関東1都6県分をタイル（PMTiles・z15）にしてアプリと同じサイトに置き（`public/data/`、約30MB）、物件の地点のタイル1枚だけを範囲指定で読んで、地点にかかる都市計画を出す。道路種別の結果を先に出し、こちらは後から読み込む。
    - 出すもの：区域（市街化区域・市街化調整区域・非線引き・都市計画区域外）、用途地域、建ぺい率・容積率（都市計画で定めた数値。角地の緩和や前面道路の幅による制限は含まない旨を添える）、防火・準防火地域、高度地区（種類・高さはデータに無いので「指定あり」まで）、地区計画（名前）、特別用途地区・風致地区・土地区画整理事業・都市計画公園・居住誘導区域など。
    - 注意が要るもの：都市計画道路の中心線が 30m 以内（整備済みも含む）、別の用途地域の境目が 15m 以内（隣の用途地域と数値も出す）。
    - 市区町村ごとにデータの有無（あり／データなし／都市計画の決定なし）と時点を `data/zoning-status.json` に持ち、データが無いものは「指定なし」ではなく「データなし」と出す。データの時点（市によっては古い）も出す。
    - スマホは市名の下に1行（「1種低層 50/100・準防火・高度地区」）で出し、押すと一覧が下から出る。一覧は同じ種類の区域（居住誘導区域と都市機能誘導区域など）を1行にまとめ、情報の多い所で画面に入りきらなければ、行の間 → 文字の大きさ → 見出しのまわりと行の高さの順に詰めてスクロールなしで収める（`components/sheet.tsx` の useDense。詰め方を書いたシートだけが詰まる）。PC はパネルのカード。PC の地図とスマホの地図（「地図を拡大」「地図で選ぶ」）は「用途地域」で色分けと都市計画道路（点線）を重ねられ、クリックした地点の用途地域も出る。
    - 色分けには凡例を添える（`components/map-legend.tsx`）。見ている範囲にある用途地域と都市計画道路だけを並べる。PC は地図の右上の道具の下に名前で、スマホの「地図を拡大」は地図の下の欄に短い名前（1種低層・近隣商業など）で、「地図で選ぶ」は地図の左上に出す。
    - 共有の文面にも添える。出典は「都市計画決定GISデータ（国土交通省）を加工して作成」と版。国のデータは参考情報で、重要事項説明などの最終確認は市の窓口・都市計画図で行う旨を必ず添える。
21. **謄本・公図を取るときの地番**（`components/parcel-card.tsx`、`adjacentParcels`）: 物件の筆と、境界が接している筆（隣地）の「所在 地番」を並べ、1件ずつ・まとめてコピーでき、登記情報提供サービスを開ける。
    - 地番で探した筆・地図で選んだ地点の筆はそのまま、住所（住居表示）で調べたときは住所の地点にある筆を「参考」として出す（住居表示と地番は別のもので、物件の土地かは公図・登記で確かめる旨を添える）。
    - 隣地は、筆のあるタイルの中で境界どうしが 0.5m 以内に近づく筆。地番の無い道路・水路に接していれば「道路（地番なし）に接しています」と書く。
    - スマホは都市計画の行の右の「地番・隣地」、PC はパネルのカード。共有の文面にも添える。証明書として使う謄本（登記事項証明書）は法務局で請求する旨も書く。
    - 隣地は押すとその筆をコピーできる小さな札にして並べる（住所の地点が道路に当たると20筆を超えることがあり、1行ずつだと画面に入らない）。スマホのシートは、建物のデータがあれば「謄本・公図用の地番」と「建物」のタブに分け、タブごとに1画面に収める。
22. **物件のまわりの道路の種別を文字で出す・MICHILU の地図に描く**（`lib/roadmap/road-read.ts`、`MapLink.read`）: 道路種別の地図が公開の ArcGIS レイヤ（CORS で読める）の市区町は、ブラウザからそのレイヤを読み、物件の地点から 50m 以内の道路の種別（凡例の名前）・方角・距離・幅員（あれば）を近い順に出す。地図の色を見比べなくても分かる。
    - 対象（25市区町）：埼玉県指定道路図の20町（町ごとのレイヤ。種別コード SYUBETU を凡例で種別名に、幅員 MIN_FUKUIN/MAX_FUKUIN）、行田市・つくば市・千代田区・日野市（種別ごとのレイヤ。Web マップのレイヤ名と色をデータに持つ）、豊島区（指定道路の線は CODE1 のコードを凡例で、公道・都道国道・4号（未完了）・区有通路の面と告示建築線はレイヤごと）。凡例に無いコードの道路は市の地図にも描かれないので出さない。
    - 八王子市は公開レイヤがあるが、種別が意味の分からないコードだけ（地図も1色）なので使わない。wagmap・Sonicweb・ALANDIS・GeoCloud などは、利用条件への同意が要る画像の地図で、データを外から読めないので対象外（リンクで開く）。東京都のオープンデータの中野区（道路ごとの代表点だけ）・品川区（2018年時点）も、精度・時点から使っていない。
    - 地図の「道路種別」（物件の市にデータがあるときだけ出る）で、見ている範囲より少し広めの道路の形を読み（z16 以上、レイヤごとに最大4000件）、市の地図の凡例の色で描く。面は薄く塗って縁取り、線は太めに。凡例（見ている範囲の種別）と「○○区の地図データ（参考）。最終確認は窓口で」を添え、クリックした地点の種別も出す。
    - スマホの「地図を拡大」は、地理院地図ではなく MICHILU の中の全画面の地図（`components/full-map.tsx`）を開く。「近くの道路」の一覧の「地図に道路種別の色を出して見る」からは、道路種別を重ねた状態で開く（背の低い画面で地図のプレビューが入らないときの入口にもなる）。凡例は地図の下の欄に出し、地図とピンを隠さない。
    - 地図に載っている道路だけで、どれが前面道路か・接道の判断はしない。「色の無い道は載っていない」「最終確認は窓口」を必ず添える。
    - スマホは地図ボタンの下に1行（「近くの道路 2項道路 北 約6m ほか1」）、押すと一覧。PC は地図ボタンの下に一覧。共有の文面にも添える。物件の緯度経度・見ている範囲は、その市の地図サービス（ArcGIS）へブラウザから直接送る（自前のサーバーは通さない）。
23. **地図の色の見方（凡例を文字で）**（`lib/roadmap/legends.ts`、`data/legends.json`）: 道路種別の地図は自治体ごとに色の付け方が違うので、地図の凡例（線の色 → 種別）を文字にして地図ボタンに添える。スマホは操作メモの後ろの「色の見方」（押すと一覧が下から出る）、PC はボタンの下に2列で出す。
    - wagmap 系（www2.wagmap.jp・マッピングぐんま・横浜市 iマッピー）の地図は、利用条件に同意したうえでレイヤ一覧（GetLayerTree）を読み、表示されるレイヤの凡例の名前と色を取る（色が画像なら画像の色を数える）。茨城県の共同の地図はレイヤが市町村ごとなので、市町村ごとに分ける。項目は「種別 → 区分 → 項目」のように下の階層にあることもある（小田原市・江戸川区など）。
    - そのほかは地図ごとに凡例を読んで書き写したもの（`scripts/legends/manual.json`、出典つき）。
      - Sonicweb（世田谷区・新宿区・練馬区・さいたま市・松戸市・土浦市・高崎市など16の地図）：地図が配る凡例の画像。
      - ICBA（千葉県・栃木県）：地図の凡例欄。
      - GeoCloud（川崎市）・open-map（八潮市）・中央区：凡例の画像。
      - ArcGIS（千代田区・豊島区・日野市）：Web マップの各レイヤの描き方（renderer）。
      - ALANDIS（千葉市・市原市・流山市・四街道市・平塚市・藤沢市・立川市・飯能市）：レイヤ一覧の色の見本、または凡例の画像。
      - machi-info（板橋区・大和市・宇都宮市）・cloudgis（桶川市）：種別のアイコンや凡例欄。
      - PDF の市（港区・北区・西東京市・和光市・志木市・富士見市・佐倉市・八千代市・桐生市）：図の PDF の凡例（色は PDF の図形の色）。凡例はどの図も同じなので、図ごとの URL ではなく案内ページの URL で引く。
    - 凡例を引くキーは地図の URL から作る（wagmap は mid、Sonicweb は theme、ALANDIS は u=、machi-info は map_id まで含める）。ALANDIS は同じパスで道路種別と市道の地図を u= で切り替えているので、市道の地図に道路種別の凡例が付かないようにしている。
    - 2026-10 時点で、道路種別の地図がある247市区町村のうち211で凡例、25で「物件のまわりの道路」と地図の道路種別（項目22）を出せる（どちらかが出るのは233）。一都三県で残っているのは、作業環境から開けない GeoCloud 系の10市区（川口・春日部・市川・我孫子・相模原・江東・杉並・武蔵野・府中・町田）と、色が1つだけの八王子市。ほかに前橋市（GeoCloud）、鹿沼市・日光市（図に凡例が無い）。
24. **調査メモを印刷・PDF 保存**（`components/print-sheet.tsx`）: 画面（地図・パネル）は印刷せず、役所調査に持っていける A4 1枚の「調査メモ」だけを出す（`app/globals.css` の `@media print`）。PC は結果の「印刷」ボタン、スマホは Safari の共有 → プリント（PDF 保存も同じ）。
    - 物件（住所・地番・緯度経度・地理院地図の URL と位置の地図）、道路種別の地図（URL・開き方・物件が載っている図・色の見方）、物件のまわりの道路、都市計画、謄本・公図用の地番、問い合わせ先と持っていくもの、窓口で聞くことと回答を書き込む欄、調べた日時、出典。
    - 印刷のあいだは PC／スマホの画面の切り替え（横幅の判定）を止める（`lib/use-desktop.ts`）。紙の幅で画面が組み替わると、都市計画などを読み直して「読み込み中」が印刷されてしまうため。

    - 埼玉県・千葉県のオープンデータサイトは、GitHub Actions（Microsoft のサーバー）からだとどのページも 403 で読めない（2026年10月）。そこの12市町のファイルは R2 の写し（`sanko/src/`）から読み、サイトに届かない市町村は前に作ったときのファイルの情報（`sanko-source.json`）を使う。

41. **周辺施設と徒歩の目安**（`lib/roadmap/poi.ts`、`components/poi-card.tsx`、`scripts/poi/build.py`）: 販売図面の「生活環境」に書く施設（スーパー・コンビニ・ドラッグストア・商業施設・病院・診療所・幼稚園と保育園・公園・郵便局・銀行・図書館・役所）を種類ごとに、物件からいちばん近いものと、施設までの徒歩の分数・道路距離を出す。
    - データ：OpenStreetMap（© OpenStreetMap contributors、ODbL）の関東の切り出し（OpenStreetMap フランスの地域の切り出し）から、名前のある施設の点（面の施設は面の点の平均の位置）を z14 の点のタイル（レイヤ poi・属性「c」種類と「n」名前）にしてアプリと同じサイトに置く（約8万3千件・約2.3MB。2026年10月）。タイルは OpenStreetMap から作ったデータベースなので、OpenStreetMap と同じ ODbL で公開する。
    - 道のり：物件から直線 1.2km 以内の施設を、種類ごとに直線で近い順に3つまで（同じ名前の点は近い方だけ）選び、最寄り駅と同じ国土地理院の道路中心線で道のりを測って、いちばん近いものを出す。徒歩の分数は道路距離 80m を1分（端数は切り上げ）。道がつながらない・直線の3倍を超える遠回りのときは直線距離の目安。
    - 施設の入口ではなく施設の位置（面の施設は面の中ほど）までの目安で、OpenStreetMap に無い施設・閉じた施設もある。広告では施設は今使えるものを物件からの道路距離か徒歩の分数で書く（不動産の表示に関する公正競争規約）ので、実際の道路距離と、施設が今もあるかを確かめる旨を画面・共有・印刷・下書きに添える。
    - 画面：スマホは最寄り駅の行を押すと出るシートの「周辺施設」のタブ（背の低い画面では駅の行を出さないので、共有・下書きで見る）、PC はパネルのカード。重説の下書きの「周辺環境」の欄（確かめる旨の1行に【要確認】）、共有の文面、調査メモ（物件の表）にも入れる。出典は「© OpenStreetMap contributors（ODbL）」（画面はデータの時点も）。

42. **上下水道・ガスの照会先**（`lib/roadmap/utilities.ts`、`lib/roadmap/data/utilities.json`）: 物件の市区町村の水道事業者（市の一部だけを受け持つ事業者は受け持つ地域も）と公共下水道の管理者を、配管図・下水道台帳の確かめ方のページと一言（「給水装置の図面は営業所で閲覧」など）つきで出す。
    - データ：1都3県の212市区町村を、事業者・市区町村・都県の公式のページで手で調べた（2026年10月）。公共下水道（汚水）の無い30町村は下水道を空にし、浄化槽・農業集落排水などを市町村の担当で確かめる旨を出す。北関東と都市ガスの導管事業者はまだ調べていない（照会先の行を出さない）。
    - 画面：都市計画のシートの「上下水道・ガス」のタブ（PC はカードの続き）。照会先が分かる市区町村は「前面道路の本管・口径・引込みの有無は、次の照会先で確認」の一言と水道・下水道の行（台帳の地図があれば「台帳の地図」の行も）、分からなければ市区町村の上下水道の担当。ガスは「ガス会社で確認」と、確かめること（都市ガスかプロパンガスか、前面道路のガス管の有無）。共有の文面と重説の下書きの「飲用水・ガス・排水施設」の欄にも照会先を入れる。

43. **国の地点データ（液状化・大規模盛土・災害履歴・将来人口・乗降客数・医療機関と幼稚園・鑑定評価書）**（`lib/roadmap/reinfolib.ts` ほか、`components/app/use-national.ts`、`scripts/reinfolib/build.py`）: 物件の地点の国のデータを、画面の部品と分けた「中身」として持つ。画面はまだつないでいない（見た目を決めてからつなぐ）。確かめるときは確認用ページ `/check?q=住所`（`?q=緯度,経度` も可）。
    - 液状化の発生傾向（`liquefaction.ts`・`useLiquefaction`）：国土交通省都市局「地形区分に基づく液状化の発生傾向図」（不動産情報ライブラリの API XKT025。250m メッシュ）の区分（非常に液状化しやすい〜液状化しにくい・評価対象外）と微地形（三角州・海岸低地 など）。地震の揺れ・敷地の盛土は見ていない旨を添える。
    - 大規模盛土造成地（`zousei.ts`・`useZousei`）：国土数値情報 A54（API XKT020）。地点が造成地の中か、50m 以内に造成地があるか（谷埋め型・腹付け型、市区町村の盛土番号）。重説の根拠には使えないので市区町村のマップで確かめる旨を添える。
    - 災害履歴（`rireki.ts`・`useRireki`）：国土調査の土地履歴調査（API XST001）。地点を含む浸水域・土砂災害・液状化などの範囲（すぐ外の 50m も）と、300m 以内の堤防決壊箇所・津波高などの記録を、時期と出典の資料つきで。調べた地域だけのデータなので、記録が無くても災害が無かったとは言わない。
    - 将来推計人口（`population.ts`・`usePopulation`）：国土数値情報 250m メッシュ別将来推計人口（R6国政局推計。CC BY 4.0。国土数値情報から直接）。物件のまわり 5×5 メッシュ（約1.25km四方）の 2020〜2050年の人口と、0〜14歳・65歳以上の割合（2025・2050年）。合計はパイプラインで済ませ、アプリは物件のメッシュの値を読むだけ。
    - 駅別乗降客数（`ridership.ts`・`useRidership`）：国土数値情報 S12（API XKT015。2011〜2023年度）。最寄り駅の事業者ごとの1日の乗降客数と合計。各社が独自に数えたもので統一の基準ではない旨を添える。
    - 医療機関・幼稚園（`facilities.ts`・`useFacilities`）：国土数値情報の医療機関（P04、2020年度）と学校（P29、2023年度。幼稚園・幼保連携型認定こども園）。まわり 1.2km の施設と、病院・診療所・小児科・内科・歯科・救急病院・幼稚園それぞれの最寄りの徒歩の目安（病床数・救急告示・災害拠点病院・診療科目つき）。保育所（福祉施設 P14）は神奈川県・横浜市が保育関係の商用利用・公開を認めていないので入れない（保育園は OpenStreetMap のまま）。
    - 地価公示の鑑定評価書（`appraisal.ts`・`useAppraisal`）：API XCT001。地価公示の地点（標準地番号）ごとに、路線価、土地・前面道路・法令の状況、2人の鑑定評価員の手法ごとの価格（比準価格・収益価格など）と取引事例・収益の内訳。
    - データの作り方：`.github/workflows/reinfolib.yml` が API（キーは GitHub の Secrets）と国土数値情報から作り、R2 の `reinfolib/<日付>/` に置く（JSON は gzip、地物は z14 の PMTiles）。データごとの置き場所・時点は `lib/roadmap/data/reinfolib-source.json`（作れなかったデータは前のまま）。3か月ごとに作り直す。API は間を空けて呼ぶ（約款：短い時間に多く呼ぶと止められることがある）。
    - 出典：API の約款の文（「このサービスは、国土交通省不動産情報ライブラリのAPI機能を使用していますが、提供情報の最新性、正確性、完全性等が保証されたものではありません」）と、データごとの出典（各モジュールの `*_CREDIT`）・注意書き（`*_CAUTIONS`）を、データを出す画面に添える。

## 保守

- **地図リンクの週次確認**: `.github/workflows/link-check.yml` が毎週月曜に `npm run check-links` を実行。役所の座標（`lib/roadmap/data/office-points.json`）でURLを作り、404・エラーページを検出すると失敗して通知される。
- **図の差し替えの追従**: `.github/workflows/sheet-watch.yml` が毎週月曜に `npm run watch-sheets` を実行。PDF の図を並べた市の一覧ページのリンクを前回の記録（`lib/roadmap/data/sheet-pages.json`）と比べ、同じ文字のリンクが別のファイルに変わっていれば（年度だけ変わった図も）データの URL を書き換え、テストが通れば main に入れる。差し替え先が1つに決まらない図は Issue（ラベル「図の差し替え」）で知らせる。
- **ChatGPT から Claude へ開発の依頼**: `.github/workflows/claude.yml`。GitHub の Issue・コメントに `@claude` と書くと、GitHub 上の Claude（claude-code-action）が作業して同じ所に返事をし、変更はブランチと PR にする（main には直接入れない）。ChatGPT の GPT のアクション（`docs/chatgpt-github-action.yaml`）から Issue を作って送れる。動かせるのはこのリポジトリに書き込める人だけ。守るルールは `CLAUDE.md`、手順は `docs/chatgpt-to-claude.md`。認証は Secrets の `CLAUDE_CODE_OAUTH_TOKEN`（Claude のサブスクリプション）。パソコンが無いときは、GitHub の Codespaces で `bash scripts/claude-token.sh` を動かすと、トークンを作って Secrets に登録できる（iPad の Safari で使える）。
- **新しい地図の自動発見**: `.github/workflows/discover.yml` が毎週月曜に `npm run discover-maps` を実行。ArcGIS Online の検索と wagmap のポータルの地図一覧から「指定道路」「道路種別」「建築基準法」などの名前の地図を探し、まだアプリに入っていないものを Issue（ラベル「新しい地図」）で知らせる。アプリに入っている地図が中で使う Web マップ・レイヤは既知として除く。知らせた地図は `discover-seen.json` に記録し、使わないと決めた地図は `discover-ignore.json` に理由を書く。2026-10 の初回でつくば市の道路種別レイヤを見つけ、「全種別」に上げた。
- **地番の地図データの更新**: `.github/workflows/parcel-tiles.yml`（毎年5月1日と手動）。G空間情報センターの公開 API で関東1都6県の地図XML（ログイン不要）を読み、都県ごとに `scripts/parcel-tiles/build_pref.py`（mojxml で筆に、tippecanoe でタイルに）でタイルを作り、tile-join で1つにまとめて Cloudflare R2 に置く。CORS を設定し、公開 URL で範囲指定して読めるのを確かめてから、`parcel-source.json` を書き換えて main に入れる。R2 の Secrets（R2_ACCOUNT_ID・R2_ACCESS_KEY_ID・R2_SECRET_ACCESS_KEY）と Variables（R2_PUBLIC_URL）が無ければ何もしない。
- **都市計画のデータの更新**: `.github/workflows/zoning-tiles.yml` が毎月2日に、G空間情報センターの全国データ（GeoJSON）の更新日時を `zoning-source.json` と比べ、更新されていれば `scripts/zoning-tiles/build.py --install` で関東分のタイルを作り直して `public/data/` に置き（版ごとにファイル名を変える）、データの有無・時点の一覧（国交省の Excel）から `zoning-status.json` を作り直す。テスト（東京駅が商業地域・防火地域など、実データで確かめる）が通れば main に入れる。外部のストレージや鍵は要らない。
- **建物のデータ（PLATEAU）**: `.github/workflows/building-tiles.yml`（1・4・7・10月の15日と手動）。PLATEAU のデータカタログ API で最新版の建築物モデルの一覧を取り、都県ごとに `scripts/building-tiles/build.py` でタイルを作り、tile-join でまとめて R2 に置く（地番と同じバケット・設定）。公開 URL で範囲指定して読めるのを確かめてから、`building-source.json`（置き場所・時点・データのある市区町村）を書き換えて main に入れる。
- **公図の筆の推定位置**: `.github/workflows/kozu-tiles.yml`（毎年5月10日と手動。都県と年を選べる）。`kozu.py --plan` が都県の地図XMLの zip を大きさで束ねて約80ジョブに分け（大きい市は図面を分ける）、ジョブごとに筆を置く（並行18本、1本 2〜3時間、`--minutes` で6時間の上限より前に置けた分で終える）。国土地理院の道路縁のタイルは1ジョブ1秒に2枚まで（全体で36枚まで）読み、市区町村ごとに R2（`kozu-src/`）に置いて次からはそれを使う。最後に `--resolve` でジョブをまたいだ重なりを外し、tippecanoe でタイルにして R2 に置き、公開 URL で範囲指定して読めるのを確かめてから `kozu-source.json` を書き換えて main に入れる。地番の地図データと同じ R2 の設定を使う。国土地理院からの読み込みは締め切りの90分前で打ち切り（山の多い広い市は1回では読み切れない）、道路縁がそろわない切れ端はその回は置かない。読めたタイルは途中で止められても R2 に置き、次の回はその続きから読む。時間切れ・失敗したジョブがあっても置けた分でまとめて main に入れ、結果の無いジョブをまとめのログに出す（Run workflow の chunks にそのジョブ、parts に前の回の置き場を入れると、そこだけやり直して足し、まとめ直す。結果の無いジョブがあるあいだはジョブごとの結果を消さない）。merge_only にすると置き直さずにまとめ直すだけ。まとめるときは、間引きで自己交差した切れ端の形を直してから重なりを測る。
- **市町村の地番参考図の筆**: `.github/workflows/sanko-tiles.yml`（毎月3日と手動）。`build.py --check` で市町村の公開ファイル（埼玉県・千葉県のオープンデータサイト、東京都・BODIK のカタログ）の更新日や大きさが前の回と違うかを見て、違えば17市町を作り直す（市町村の zip 約0.5GB と法務省の地図XML 約0.8GB を読み、約1時間）。R2 の `sanko/` に置き、公開 URL で範囲指定して読めるのを確かめてから `sanko-source.json` を書き換えて main に入れる。地番の地図データと同じ R2 の設定を使う。

    - 本物の雲・雨・雷（`lib/app/satellite.ts`）：気象庁のひまわり画像（日本域の z6 タイル 1 枚＝東京のまわり 500km、約 2km/画素。可視 B03 と赤外 B13、2.5 分ごと・公開は約 8 分遅れ。「今 − 8 分」から 2.5 分刻みでさかのぼって最初に読めたもの）から、低い雲（R）・高い雲（G）・明るさ（B）の場を作る。昼は可視の反射率で濃さ、赤外の温度で高さ。夜は赤外だけ（いちばん暖かい 1 割を地面として、それより冷たい所を雲）なので、低い雲は予報の雲量で補う。シェーダーは低い雲（1.4km）と高い雲（7.5km）の 2 つの層を地球の丸みに沿って置き、視線がそれぞれの層に当たる所の値を読んで、細かい模様で 2km の画素の中を埋める。高い雲は日没後もしばらく日が当たり桃色に残る（7.5km の高さに届く太陽の光の色で）。太陽の隠れ具合・雲の影も同じ場から（本物の雲の影が街に落ちる）。雲は地上の風の 2 倍で流れる。読めたときは 1.5 秒で切り替え、読めないときは雲量だけの模様。カメラのまわり約 25km の雲量を CSS の色と街の照明にも使う。
    - 雨の幕：高解像度降水ナウキャスト（5 分ごと。z8 タイル 2×2＝西〜南西 180km、約 0.6km/画素）の雨の強さ（mm/h）を、視線が雲の底（1.4km）より下を通る分だけ積分して灰色に溶かす（遠くの雨柱、近くの雨。減衰は 0.2×R^0.63/km）。手元の雨の筋の強さもレーダーのカメラ位置の値（mm/h ÷ 15）。雷ナウキャスト（10 分ごと）に発雷域があれば、その向きの雲と空が 22 秒に 1 回ほど 2 回ちらつく（遠いほど弱く、150km より遠くは出さない）。#w= で天気を固定しているときは衛星・レーダーを使わない。#sat=YYYYMMDDhhmmss（UTC）でひまわりの時刻を固定できる。
    - カメラの処理（スマートフォンと同じ）：近い所は霞を弱める（空気の濁りの係数を、2km 以内は 5〜7%、20km より遠くは 100% に。本物の写真は 1〜3km の建物の日陰もほぼ黒く締まる。近い霞は空の青ではなく中立の色）。街と塔は彩度を少し上げ、中間の明るさの差を広げる（空は CSS の色とそろえるため変えない）。暗い所に動かない細かい粒。
    - 露出と薄明：露出の節は本物のスマートフォンに合わせ、薄明で大きく上げる（太陽 10° で 1.1、0° で 2.6、-6° で 30、-12° で 90）。単一散乱だけでは薄明の空が紫がかった灰色になるので、輝度はそのままに高い所ほどブルーアワーの青へ寄せる（`twilightTint`。太陽の側の地平線の橙は残す。シェーダー・CSS の色・<head> の最初の計算で同じ式）。明るさが一定の光（窓・街灯・車・東京タワー・夜空の街明かりの照り返し）は露出の比（夜を 1、日没で約 0.03、-6° で 0.33）で強くなる：日没のころは目立たず、ブルーアワーに浮かび上がる。太陽の本体は空よりずっと明るい（地平線の近くで大気に弱められても空に溶けず、白〜黄に飽和し、ごく低いと橙。雲を重ねた後に足し、雲のすき間からだけ見える）。にじみは届く光の色で、低い太陽でも金〜橙に光る。
    - 夜景：夜空は灰色がかった紺、地平線の近くは茶色がかった灰色（紫にならない）。街明かりが霞を照らす分は街の上の空気だけで、遠くの山は地平線の空より暗いシルエット。窓の明るさは窓ごとに大きく違い（明るい事務所の階は白く飛ぶ）、遠くの窓は画素ごとの明るさを裾の重い乱数で散らして点の海に（平均は同じ）。窓と街灯のまわりに光のにじみ。東京タワーの色は画面の色（sRGB）から線形に直す（橙が薄い桃色にならない）。
    - 曇り・雨・雪：雲の底を照らす空の光は曇るほど青みが抜けて灰色、厚い雲は地平線まで覆い、すき間から晴れの空が見えない。厚い雲は夕焼けを通さない（明るさだけ空に合わせた灰色、夜は街明かりで茶灰色）。曇りの日の遠くの霞は雲の底の色。
    - 画素のなめらかさ：焼き込みは画面の 4 倍（4716×3300）で描き、カメラのレンズと同じ形（ガウス＋画素の箱、合わせて標準偏差 0.55 画素）で縮める（平均だけだと輪郭が階段状に残り、拡大するとブロックに見える）。窓のきらめきの乱数は画面の画素ではなく窓の鍵から。ピンチで拡大しているときは、その倍率（2 倍まで）でキャンバスを描き直す（`visualViewport` の scale。引き伸ばしで四角くならない。絵の画素数は画面と同じなので、それ以上は写真と同じくぼける）。
    - 航空障害灯（航空法の決まり。`scripts/city-bake/post4.py`）：60m 以上の建物の屋上の両端に赤い灯、90m 以上は赤の明滅（中光度赤色、毎分 20〜60 回＝周期 1.4〜2.6 秒、点灯 45%）、150m 以上と東京タワーの頂は昼は白い閃光（中光度白色。周期の 12%、日の出前 3° から）で夜は赤の明滅。105m を超える建物は中間の高さ（52.5m 以下の等間隔）にも不動の赤。同じ建物の灯は同期、建物どうしは位相がずれる。昼の閃光だけのコマは合成した絵（`frameT`）を使い回して 6 コマ/秒（分が変わったら描き直す）。
    - 目立つ高層ビルの外装（`scripts/city-bake/facades.json`、post2）：PLATEAU の空中写真の質感は 1 画素 0.5〜1m でぼやけるので、愛宕グリーンヒルズ MORI・フォレスト、麻布台ヒルズ レジデンスA、アークヒルズ仙石山森タワー、泉ガーデンタワー、六本木グランドタワー、六本木ヒルズ森タワー、ミッドタウン・タワーは、実際の階数で各階の帯・ガラス・方立を描く（ガラスは窓として扱い、夜の点灯と空の映り込みが付く。色は写真から）。形は PLATEAU のまま。東京タワーは大展望台からトップデッキへのエレベーターの軸（中央の密な格子の筒）を持ち、上の段の部材は本物の太さ（X 1.0m・梁 0.85m）なので、格子のすき間から街が透けない（24 画素/pt の焼き込みでの充填は 130m より上で 94〜98%）。塔の層の縮小ぼかしは街より小さい 0.35 画素（0.55 だと幅 11 画素の塔の半分近くが半透明の縁になる）。
    - 写真らしさ：空からの光は建物どうしの照り返しで青みが薄まる（空の光の彩度を 45% 落とし、地面の照り返しは暖かい灰色 0.16）。建物の間（空の見え方が小さい所）は暗い。窓は空を映す（フレネル。オフィスの熱線反射ガラスは正面でも 12%、斜めから見るほど鏡に近づく。太陽の映り込みはきらりと光る。写真の質感のある建物は質感に窓が写っているので、窓の型ではなく用途ごとの一様なガラスの割合で映す）。東京タワーは格子なので、面の向きによらず昼は日が当たる（高さ地図では自分の影にしない。部材は遠目の密度に合わせて少し太め）。東京の夜空は明るいので星は明るいものだけ（下の「星空」）。焼き込んだ色は縮小で柔らかくなった分を少し研ぐ（カメラの輪郭強調と同じ程度）。
    - 湿度（`lib/app/air.ts`）：霞の粒は湿度が高いと水を吸ってふくらみ光をよく散らす。気象庁の湿度と季節（冬は大陸の澄んだ空気、夏はもや・光化学スモッグ）から霞の量 aero を決め、大気の式のミー散乱（地表近くの層。上空の薄い霞は湿度によらず、日没後の西の赤みのもと）、太陽と月のにじみの広がり、遠くの霞（見通し＝コシュミーダーの式。同じ係数）、星の見え方、夜の空の明るさ（街の明かりが霞で散る）に使う。見通しは乾いた冬の 30% で約 105km（富士山がくっきり）、10 月の 50% で約 29km、夏の 65% で約 12km、88% で約 6km。CSS の色と <head> の最初の計算も同じ（湿度は端末に覚えた観測から。#…&h=30 で固定できる）。
    - 星空（`lib/app/stars.ts`）：本物の星。3 等より明るい恒星 93 個（イェール輝星星表の J2000 の赤経・赤緯に歳差を足し、グリニッジ恒星時から東京駅での高度・方位に。大気の屈折も）と惑星 5 つ（水星・金星・火星・木星・土星。JPL の近似ケプラー軌道要素（1800〜2050 年）で日心の位置を出し、地球から見た向きに。明るさは距離と位相角から）を、カメラの投影で画面の位置に点として描く（`present()`。点の大きさは明るいほど大きく、1 を超える明るさは中心が白く飛ぶ＝写真の明るい星。色は色指数 B−V から青白〜橙）。東京の夜空は街明かりで明るいので、大気の減光（空気量×0.3 等）を足して 3.2 等までしか出さず、合成した絵の α に「空の見える度合い」（空の明るさ＝薄明・街明かりの照り返し・太陽と月のにじみで消え、地平線から 15° 以下は見えない。雲・街・塔・雨の幕・霧の後ろも見えない）を入れて掛ける。明るいものほど早く見える（金星は日没の直後、0 等は太陽 −8°、2 等は −13° でいっぱいに）。霞が濃いと薄れる（`air.stars`）。低い星ほど大きくまたたき（5 回/秒の乱数をなめらかに）、惑星はほとんどまたたかない。動きを減らす設定では止める。月は SunCalc の実位置と満ち欠け。天の川は東京の空では見えないので描かない。人工衛星・飛行機・流れ星も描かない。春分・衝・合の日付と北極星の位置のテストつき。
    - 出典は「その他」の「データの出典と時点」に「街並み（ホームの帯）」として表示（PLATEAU・地理院タイルを加工して作成）。

    - Google の決まり（Map Tiles API のポリシー）：表示している間は Google Maps のロゴ（高さ 16pt、まわりに上・左右 10pt、下 5pt の余白。忙しい背景には縁取りの版）と、見えているタイルの出典を 1 行で、描いた絵の下の方に出す（帯に重なるカードの上端の上、右寄せ。どこが Google かが分かるよう「街並み」と添える）。絵は保存しない（端末にも残さない）。地図の表示以外（画像の解析・形の抜き出し）に使わない。「その他」の「データの出典と時点」に、街並みが Google であること、空・天気・明かり・東京タワーの照明は MICHILU が描いたものであること、Google マップ／Google Earth 追加利用規約と Google プライバシーポリシーのリンクを出す。Google の利用規約には Google 以外の地図と一緒に使わない決まりがあるので、地理院の地図を出す画面（物件の画面・地図）には Google の街を出さない。
    - 検証：`#city3d=off` で今までの街、`#city3d=plateau` で港区の PLATEAU（2025・LOD2・質感なし。鍵が無くても位置・距離・面の向き・合成を確かめられる。形が重く約 300MB）。読み込みの記録（表示したタイルの数・断ったタイル・メモリ）はブラウザのコンソールに出す。

58. **ホームを届いたデザインに（夕焼けの街の写真）・下のメニューと右上のメニュー（≡）を作り直す**（`components/app/home.tsx`、`components/app/frame.tsx` の `BottomNav`、`components/app/mobile-app.tsx`、素材は `public/home/sunset-900.webp`・`sunset-1260.webp`・`sunset-1620.webp`（届いた 3764×6684 の絵を縮めた3枚。画面に合う大きさを端末が選ぶ）・`public/home/logo-mark-white.webp`）: 届いたデザインと背景の絵のとおり、画面いっぱいの夕焼けの街の写真（下のメニューの後ろまで敷く）の上に、上から：ロゴ（今までのマークと MICHILU の白い版。前の白いロゴから小さい副題を消したもの）と右上のメニュー（≡）、「不動産の現場に、／すぐ使える情報を。」、住所・地番の検索欄（明るいすりガラス。キーボードの「検索」か、字を入れると出る → で調べる。調べている間は欄の右に「調べています」）、写真の街並みを見せる空き（画面の高さに合わせて伸び縮みし、背の低い画面でもスクロールせずに収まる）、最近の検索（暗いすりガラスの一覧に3件。1行目は市区町村と町名、2行目は「地番：12-5」「番地：1-2-3」、地図で選んだ所は「地図で選んだ場所」。直近7日に見ていた物件には「続きから」）。写真の上の字は白に薄い影。PC は変えない。
    - まだ何も調べていないときは、最近の検索の代わりに「はじめての方へ」（住所と地番の例。押すとそのまま調べる）。
    - 右上のメニュー（≡）は、ときどき使うものを4つの章に：調べる（地図で場所を選ぶ。住所の無い土地も選べる）／お知らせ・使い方（お知らせは未読の印と「新着」。≡ にも印）／データ（対応している市区町村の数・データの出典と時点・調査記録の書き出し・読み込み）／アプリ（ホーム画面に追加・アカウント・その他のページ）。
    - 下のメニューは、よく使う4つ：検索（ホーム）・お気に入り・履歴・書類・出力（アイコン24pt・名前11pt）。地図で場所を選ぶ画面は ≡ から開く（一時、下のメニューに「地図」を置いたが外した）。ホームでは写真の上の暗いすりガラス（上の角を丸め、選んでいる所は青い字と下の線）、ほかのページは白。その他のページは ≡ の「アカウント・その他」から開く。
    - ホームの帯の時間連動の空と街（54〜57）はやめ、届いた写真で固定。下のメニューのページの帯は今までどおり時間連動の空と街。時刻・電池の帯の色は、ホームでは写真のいちばん上の空の色（#386fab）。
    - 浮き上がる動き（`.home-rise`）とページの切り替えの動き（`.page-in`）は、終わったら外す（`animation-fill-mode: backwards`。終わりの形は元の見た目と同じ）。動きが残ったままの箱の中では、すりガラスの後ろがぼけないため。浮き上がる動きは、すりガラスの箱そのものに付ける。
